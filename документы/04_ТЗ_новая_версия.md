## 1. Постановка задачи

Существующая программа (Qt 5 + OpenSceneGraph + osgEarth) выполняет свою
функцию, но имеет накопившиеся проблемы: устаревший рендер, «плоская» картинка
без атмосферы и освещения, тяжелые зависимости (osgEarth + GDAL), смешение
расчетной логики с отрисовкой, хрупкие места с единицами измерения и системами
координат (см. [журнал](03_журнал.md)).

**Цель:** создать с нуля программу Kos 2.0, которая:

- отображает **фотореалистичную Землю** (дневная/ночная стороны, облака,
  атмосферное свечение, блики океана) и **космос** (звездное небо);
- загружает КА из **TLE** и показывает их движение по орбитам в реальном
  и ускоренном времени;
- держит **стабильные 60 FPS** при сотнях КА на средней машине;
- архитектурно готова к расширению: БПЛА, зоны покрытия (конусы), линии
  видимости, 2D-карта QMapControl — добавляются без переделки ядра.

**Объем первой версии (MVP):** Земля + космос + время + 2–10 КА из TLE-файла
с орбитными треками. БПЛА и зоны покрытия — в последующих версиях, но
интерфейсы под них закладываются сразу (раздел 7).

## 2. Требования

### Функциональные (MVP)

| № | Требование |
|---|---|
| Ф-1 | Загрузка TLE из файла (формат celestrak, несколько КА в одном файле) |
| Ф-2 | Прогноз движения КА моделью SGP4/SDP4 (не Кеплером!) |
| Ф-3 | 3D-сцена: Земля с текстурами день/ночь, облака, атмосфера; звездный фон |
| Ф-4 | Вращение Земли по звездному времени, положение Солнца по модельному времени |
| Ф-5 | Отображение КА (маркер/модель), подпись, орбитный трек |
| Ф-6 | Управление временем: пауза, реальное время, ускорение ×10…×10000, прыжок к дате |
| Ф-7 | Камера: орбитальный облет, зум от поверхности до полного диска, инерция |
| Ф-8 | Выбор КА кликом → карточка с параметрами (высота, скорость, элементы) |

### Нефункциональные

| № | Требование |
|---|---|
| Н-1 | ≥ 60 FPS при 500 КА и полной Земле в кадре (GTX 1650 / встроенная Iris Xe) |
| Н-2 | Расчеты отделены от рендера: ядро собирается и тестируется без GUI |
| Н-3 | Единые соглашения: расчеты — км и радианы, сцена — метры, углы API — документированы в каждом заголовке |
| Н-4 | Юнит-тесты баллистики против эталонных векторов SGP4 (из статьи Vallado) |
| Н-5 | Время холодного старта ≤ 3 с (текстуры грузятся асинхронно, с заглушкой) |
| Н-6 | Кроссплатформенность Windows/Linux (сборка CMake) |

### Требования расширяемости (не реализуются в MVP, но учитываются)

- **Р-1 (БПЛА):** любой движущийся объект реализует общий интерфейс
  `IDynamicObject` (позиция от времени) — БПЛА добавится как еще один класс;
- **Р-2 (зоны и видимость):** геометрия конуса и надирная проверка переносятся
  из Kos 1.0 (они уже правильные — см. журнал);
- **Р-3 (QMapControl):** состояние КА/БПЛА публикуется через общую модель,
  на которую подписываются И 3D-сцена, И 2D-карта (раздел 7).

## 3. Главный вопрос: Qt или Python

Разберем честно, потому что от этого зависит все остальное.

### Заблуждение, которое надо снять сразу

> «Для красивой анимации и моделей придется использовать Python, а потом
> подключать его через конвертирование»

**Это не так.** Красота 3D-картинки не зависит от языка программирования.
Она делается тремя вещами: **текстурами** (какие данные натянуты на сферу),
**шейдерами** (программы для видеокарты: атмосфера, блики, ночные огни) и
**постобработкой** (bloom, тонмаппинг). Все это исполняется на GPU и одинаково
доступно из C++ и из Python — язык лишь отдает команды видеокарте. Python
популярен в 3D-туториалах из-за простоты примеров, а не из-за графических
возможностей.

Более того: связка «красивое ядро на Python + основная программа на C++/Qt
через конвертирование» — худший из вариантов. «Конвертировать» Python в C++
автоматически нельзя (Nuitka/Cython не переводят код в поддерживаемый C++,
а лишь упаковывают интерпретатор); встраивание интерпретатора Python в
C++-приложение (CPython API / pybind11) — это два рантайма, ад с упаковкой,
GIL, версиями библиотек и отладкой на стыке. Так делают только ради готовых
уникальных Python-библиотек, которых здесь нет.

### Сравнение честных вариантов

| Критерий | C++ / Qt 6 | Python / PySide6 (тоже Qt!) | Гибрид C+++Python |
|---|---|---|---|
| Красота картинки | одинаково (шейдеры те же) | одинаково | одинаково |
| Скорость разработки | средняя | выше | самая низкая (стык) |
| Производительность расчетов | максимум | достаточная (sgp4 — C-ядро, numpy) | — |
| **QMapControl** | **работает напрямую** | ✗ нет биндингов — нужно писать Shiboken-обертку | работает |
| Переиспользование кода Kos 1.0 | напрямую (C++) | переписывать | частично |
| Распространение (exe) | windeployqt, просто | PyInstaller, тяжелее и капризнее | очень тяжело |
| Один рантайм | да | да | **нет** |

### Вывод

**Полный Qt 6 / C++ — правильный выбор для этого проекта.** Решающие аргументы:

1. **QMapControl** — C++-виджетная библиотека, уже используемая в проекте.
   Из Python ее использовать нельзя без написания собственных биндингов —
   это недели работы ради нуля пользы.
2. Весь наработанный расчетный код Kos 1.0 (SGP4, преобразования координат,
   геометрия видимости) — C++ и переносится копированием.
3. Один язык, один рантайм, простая сборка и поставка.

**Законная роль Python в проекте** (рекомендуется!) — офлайн-инструменты,
которые не входят в поставку:

- подготовка текстур: склейка/пережатие NASA-карт, генерация карты нормалей
  из карты высот (Pillow, numpy);
- генерация процедурного шума для облаков (opensimplex/noise → PNG);
- прототипирование формул и проверка эталонов SGP4 (пакет `sgp4`) — удобно
  сверять с ним юнит-тесты C++-ядра;
- скрипты скачивания свежих TLE с celestrak.

## 4. Анализ вариантов рендеринга

Внутри мира Qt есть четыре пути. Сравним.

### Вариант A — Qt Quick 3D (рекомендуется)

Современный 3D-движок Qt 6 поверх RHI (автоматически Vulkan / D3D11 / Metal /
OpenGL). Сцена описывается декларативно в QML, данные и логика — в C++.

- ✅ **Custom materials на GLSL** — свои шейдеры атмосферы/океана/ночных огней;
- ✅ PBR-материалы, HDR-скайбокс, bloom/тонмаппинг из коробки (ExtendedSceneEnvironment);
- ✅ **инстансинг** из коробки — тысячи КА одним draw call;
- ✅ QML-анимации (плавные переходы камеры, появление подписей) — то самое
  «красиво анимировать» бесплатно;
- ✅ активно развивается, это будущее Qt-3D;
- ⚠️ встраивание в виджетное приложение — через `QQuickWidget` (штатно).

### Вариант B — «сырой» OpenGL в QOpenGLWidget

Полный контроль, максимум производительности, ноль лишних зависимостей.

- ✅ идеален для одиночного специализированного объекта (глобус);
- ❌ все руками: загрузчики, текст, пикинг, анимации, свет, пост-эффекты;
- ❌ объем кода в 3–5 раз больше; «красота» достижима, но дорога.

Разумный **запасной вариант**, если Qt Quick 3D чем-то не устроит: шейдеры
Земли (раздел 6) переносятся в него без изменений.

### Вариант C — остаться на OpenSceneGraph/osgEarth

- ❌ проект OSG в полузаморозке, osgEarth тянет GDAL/PROJ (сотни МБ);
- ❌ фиксированный конвейер в старом коде, современные эффекты — боль;
- ❌ это ровно то, от чего уходим. Не рассматриваем.

### Вариант D — Qt 3D (модуль qt3d)

- ❌ фактически заморожен в Qt 6, сам Qt рекомендует Quick 3D. Не рассматриваем.

**Итог: вариант A (Qt Quick 3D), запасной — B (чистый OpenGL).**

## 5. Рекомендуемый стек

```
Язык:            C++17
Фреймворк:       Qt 6.8 LTS (модули: Core, Gui, Widgets, Quick, Quick3D, QuickWidgets)
Сборка:          CMake ≥ 3.21 (вместо qmake — стандарт Qt 6)
Рендер:          Qt Quick 3D + custom materials (GLSL через Qt Shader Tools)
Баллистика:      собственная библиотека kos_core (C++, без Qt-GUI зависимостей):
                 SGP4/SDP4 (перенос из Kos 1.0 или эталонный код Vallado),
                 преобразования СК, звездное время, Солнце
2D-карта:        QMapControl (имеющаяся, C++/Widgets) — этап 9
Тесты:           Qt Test или Catch2, эталонные векторы SGP4
Офлайн-скрипты:  Python 3 (Pillow, numpy, sgp4, noise) — подготовка ассетов
Профилирование:  Qt Creator QML Profiler, RenderDoc
```

Структура окна: приложение остается **виджетным** (ради QMapControl и привычных
панелей), 3D-сцена живет в `QQuickWidget` как одна из вкладок/панелей:

```
QMainWindow
├── QToolBar / панель времени (Widgets)
├── QTabWidget
│   ├── вкладка «3D»  → QQuickWidget → QML: View3D (Quick 3D сцена)
│   └── вкладка «2D»  → QMapControl::MapControl (этап 9)
└── QDockWidget «Список КА», «Свойства» (Widgets)
```

## 6. Из чего складывается «красивая Земля»

Рецепт по слоям — каждый пункт = конкретный ассет + кусок шейдера:

| Слой | Данные | Эффект в шейдере |
|---|---|---|
| 1. Рельеф суши и океаны | NASA Blue Marble NG, 8k–16k (public domain) | базовый цвет (albedo) |
| 2. Ночные огни городов | NASA Black Marble, 8k | подмешивается на теневой стороне: `mix(night, day, smoothstep(терминатор))` |
| 3. Блик Солнца на океане | маска вода/суша (спекуляр-карта) | specular только по воде — «живой» солнечный зайчик |
| 4. Микрорельеф | карта нормалей из ETOPO/SRTM (генерируется Python-скриптом) | горы ловят свет на терминаторе |
| 5. Облака | карта облачности NASA + **FBM-шум** для детализации и медленной эволюции | отдельная сфера R×1.003, своя скорость вращения, полупрозрачность, тень на поверхность (опция) |
| 6. Атмосфера | — (чистая математика) | ободок рассеяния: fresnel-градиент голубого на лимбе + рыжение у терминатора; при желании — полная модель Bruneton (этап «полировка») |
| 7. Космос | панорама Млечного Пути ESO/NASA SVS, HDR | скайбокс + слабый bloom на Солнце |
| 8. Солнце | позиция из модельного времени (перенос SunPosition.cpp) | DirectionalLight сцены = реальное направление на Солнце |

Про «хороший шум»: облака и легкая неоднородность атмосферы делаются
**FBM-шумом** (fractal Brownian motion — сумма октав Перлин/симплекс-шума).
Дешевый путь — запечь шум в текстуру Python-скриптом и скроллить/смешивать две
копии в шейдере (быстро, красиво). Дорогой путь — считать 3D-шум прямо в
шейдере (гибче, но тратит GPU). Для MVP — запеченный, этого достаточно.

**Геометрия глобуса:** сфера ~64×128 сегментов (≈16k треугольников) — при
текстурах 8k выглядит идеально и стоит копейки. Квадродерево тайлов (как в
osgEarth) НЕ нужно, пока нет задачи прижиматься камерой к рельефу.

## 7. Архитектура

Главный принцип, исправляющий грех Kos 1.0: **ядро не знает про рендер**.

```
┌────────────────────────────────────────────────────────────────┐
│  kos_core  (C++ библиотека, БЕЗ GUI, покрыта тестами)          │
│                                                                │
│  TleParser     → набор ScTle                                   │
│  Sgp4Propagator: (ScTle, t) → r,v в АГЭСК [км]                 │
│  Frames:  AGESC↔GSC(t), GEO↔GSC, звездное время S(t)           │
│  SunModel: t → направление на Солнце                           │
│  IDynamicObject: интерфейс «позиция от времени»                │
│     ├── SatelliteObject (SGP4)          ← MVP                  │
│     └── UavObject (ортодромия)          ← будущее, Р-1         │
│  VisibilityMath: надирный угол, γ_max   ← будущее, Р-2         │
└──────────────────────────┬─────────────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────────────┐
│  SimulationEngine  (QObject, отдельный поток)                  │
│  - модельные часы: пауза / ×N / прыжок                         │
│  - фиксированный шаг физики + интерполяция для рендера         │
│  - на каждый тик: массив состояний всех объектов               │
│  - сигнал stateChanged(SnapshotPtr)  ← единственный канал      │
└──────┬───────────────────────────────────────┬─────────────────┘
       │ (подписчик 1)                         │ (подписчик 2, этап 9)
┌──────▼──────────────────────┐   ┌────────────▼───────────────┐
│  Сцена 3D (QML/Quick 3D)    │   │  2D-карта (QMapControl)    │
│  глобус, КА, треки, время   │   │  подспутниковые точки,     │
│  = чистое «представление»   │   │  трассы на карте           │
└─────────────────────────────┘   └────────────────────────────┘
```

Ключевые решения:

1. **Snapshot-модель.** Движок раз в тик публикует неизменяемый снимок состояний
   (id, r_агэск, r_гск, широта/долгота, скорость). 3D и 2D просто отображают
   снимок. Ни одно представление ничего не считает само — поэтому 3D-сцена и
   карта не могут «разъехаться» (урок Kos 1.0, где конус и линии считали
   видимость по-разному).
2. **`IDynamicObject`** — задел под БПЛА: движку все равно, спутник это или
   дрон, у обоих есть `stateAt(t)`. БПЛА в будущем = один новый класс в ядре
   + один делегат отображения.
3. **Единицы:** ядро — км/радианы/UTC; конверсия в метры — только на границе
   с QML. Одна функция, одно место, один комментарий.

## 8. Методы обеспечения производительности

| Метод | Что дает |
|---|---|
| Расчеты в отдельном потоке (`SimulationEngine`) | GUI никогда не подтормаживает от SGP4; связь через сигнал со снапшотом |
| Фиксированный шаг физики + интерполяция кадров | плавность при любом FPS; нет «перепрыгнутых» событий |
| **Инстансинг** КА (один меш → N экземпляров, буфер трансформаций) | 10 000 маркеров = 1 draw call |
| Орбитные треки как предвычисленные полилинии, пересчет раз в N минут модельного времени | треки не считаются каждый кадр |
| Подписи только для выбранных/ближних КА | текст — самое дорогое в сцене |
| Текстуры: BC7/DXT-сжатие, mip-уровни, асинхронная загрузка | быстрый старт (Н-5), меньше видеопамяти |
| LOD: маркер-точка вдали ↔ 3D-модель вблизи | детализация там, где ее видно |
| Профилирование каждым этапом (QML Profiler + RenderDoc), бюджет кадра 16.6 мс | деградация ловится сразу, а не в конце |
| SGP4 батчем по массиву КА (SoA-раскладка, при желании OpenMP) | 1000 КА ≈ доли миллисекунды на тик |

| Панорама Млечного Пути | ESO Milky Way panorama / NASA SVS Deep Star Maps |
| TLE | celestrak.org (актуальные), файлы из Kos 1.0 для тестов |
| 3D-модель КА (простая) | NASA 3D Resources (public domain) или свой low-poly |

## 10. План реализации по этапам

Каждый этап заканчивается работающей программой и критерием приемки (КП).
Ориентировочная трудоемкость — в «условных неделях» одного разработчика,
знакомого с Qt, но не с 3D (первые этапы включают обучение).

| # | Этап | Содержание | КП — что должно работать | Оценка |
|---|------|-----------|--------------------------|--------|
| 0 | Каркас проекта | CMake, Qt 6.8, git, структура kos_core/kos_app, CI-сборка, пустое окно с QQuickWidget | проект собирается на Win/Linux одной командой | 0.5 |
| 1 | Сцена и камера | View3D, перспективная камера, орбитальный контроллер (тач/мышь, инерция, зум-лимиты), серый шар-заглушка | шар вращается мышью плавно, 60 FPS | 1 |
| 2 | Земля v1 | сфера с дневной текстурой 8k, DirectionalLight-Солнце, вращение по S(t) (перенос compSiderealTime) | узнаваемая Земля крутится с правильной скоростью | 1 |
| 3 | Космос | HDR-скайбокс Млечного Пути, экспозиция/тонмаппинг, легкий bloom | «космическая» картинка без засветов | 0.5 |
| 4 | Земля v2 — красота | custom material: ночные огни с мягким терминатором, спекуляр океана, карта нормалей; слой облаков с FBM-шумом; fresnel-атмосфера на лимбе | скриншоты «как из Space Engine»; FPS ≥ 60 | 2 |
| 5 | Ядро баллистики | kos_core: TleParser, Sgp4Propagator, Frames, SunModel; юнит-тесты против эталонных векторов Vallado и python-sgp4 | тесты зеленые, ошибка ≤ 1 км против эталона | 1.5 |
| 6 | КА в сцене | SimulationEngine (поток, снапшоты), маркеры КА инстансингом, подписи, орбитный трек, клик-выбор → карточка параметров | 2–10 КА из файла TLE летают по орбитам, треки корректны | 1.5 |
| 7 | Машина времени | пауза/×N/прыжок к дате; Земля, Солнце и КА согласованы на любом ускорении; интерполяция между тиками | на ×1000 движение плавное, терминатор ползет правильно | 1 |
| 8 | Производительность | стресс 500–5000 КА (starlink.txt), профилирование, инстансинг/LOD/потоки по результатам | 500 КА ≥ 60 FPS, 5000 КА ≥ 30 FPS | 1 |
| 9 | 2D-карта | вкладка QMapControl, подписка на те же снапшоты: подспутниковые точки и трассы; синхронный выбор КА 3D↔2D | клик по КА в 3D подсвечивает его на карте и наоборот | 1.5 |
| 10 | Задел БПЛА и зон | перенос из Kos 1.0: VisibilityMath (надирная проверка, γ_max), UavObject (ортодромия) в kos_core с тестами — UI пока не делается | тесты математики зеленые; ядро готово к БПЛА-этапу | 1 |

**Итого MVP (этапы 0–7): ~9 недель; полный план: ~12.5.** Этапы 2–4 можно
вести параллельно с 5 (разные люди: «графика» и «ядро»).

**Порядок важен:** сначала выглядит (этапы 1–4 дают мотивацию и материал для
демонстраций), потом летает (5–7), потом быстро (8), потом интегрируется (9–10).

## 11. Риски

| Риск | Вероятность | Смягчение |
|---|---|---|
| Qt Quick 3D не даст нужного эффекта атмосферы штатными средствами | низкая | custom materials = произвольный GLSL; запасной вариант B (чистый OpenGL) с теми же шейдерами |
| Слабые GPU у целевых пользователей | средняя | переключатель качества: без облаков/атмосферы; текстуры 4k вместо 8k |
| Ошибки переноса SGP4 | средняя | этап 5 начинается с эталонных тестов, сверка с python-sgp4 |
| QQuickWidget + Widgets: артефакты совместного рендера | низкая | известная связка; при проблемах — QWidget::createWindowContainer |
| Расползание объема («еще чуть-чуть красоты») | высокая | жесткие КП этапов; все «хотелки» — в бэклог после этапа 8 |
| Устаревание TLE в демо-данных | высокая | Python-скрипт обновления с celestrak в репозитории |
